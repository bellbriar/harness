## Rules that run

### bb-img-alt

**Images have text alternatives.** WCAG 1.1.1 ([Understanding](https://www.w3.org/WAI/WCAG21/Understanding/non-text-content.html)) · Tier 1 · checked by Bellbriar, on the markup · basis `sc`: a FAIL is a failure of each criterion the rule cites, one W3C names (a W3C failure technique, or an ACT rule W3C's Working Group approved).

W3C ACT rules: [23a2a8](https://www.w3.org/WAI/standards-guidelines/act/rules/23a2a8/) Image has non-empty accessible name (approved); [59796f](https://www.w3.org/WAI/standards-guidelines/act/rules/59796f/) Image button has non-empty accessible name (approved).

**Why it matters.** A screen reader cannot describe an image that has no text alternative: it reads out the file name or skips the image, so what it shows is lost to people who cannot see it.

**How to fix it.** Give every image that carries information an alt attribute that says what it shows or does. Give a purely decorative image an empty alt (alt=""), so screen readers skip it.

HTML, before:

```html
<img src="team.jpg">
```

HTML, after:

```html
<img src="team.jpg" alt="Our five-person support team">
```

React:

```jsx
<img src={teamPhoto} alt="Our five-person support team" />
```

Vue:

```vue
<img :src="teamPhoto" alt="Our five-person support team">
```

### bb-svg-name

**svg[role=img] has accessible name.** WCAG 1.1.1 ([Understanding](https://www.w3.org/WAI/WCAG21/Understanding/non-text-content.html)) · Tier 1 · checked by Bellbriar, on the markup · basis `sc`: a FAIL is a failure of each criterion the rule cites, one W3C names (a W3C failure technique, or an ACT rule W3C's Working Group approved).

W3C ACT rules: [7d6734](https://www.w3.org/WAI/standards-guidelines/act/rules/7d6734/) SVG element with explicit role has non-empty accessible name (approved).

Checks svg elements whose role is img or ARIA 1.3's synonym image (the first role token a browser knows).

**Why it matters.** An &lt;svg&gt; marked role="img" is announced as an image, and its drawing is not read: without a name, users hear only "image".

**How to fix it.** Name it with aria-label, or with a &lt;title&gt; as its first child that aria-labelledby points to. If the graphic is decorative, drop role="img" and add aria-hidden="true" instead.

HTML, before:

```html
<svg role="img" viewBox="0 0 24 24">
  <path d="M3 12h18"/>
</svg>
```

HTML, after:

```html
<svg role="img" aria-label="Rated 4 out of 5" viewBox="0 0 24 24">
  <path d="M3 12h18"/>
</svg>
```

React:

```jsx
<svg role="img" aria-label="Rated 4 out of 5" viewBox="0 0 24 24">
  <path d="M3 12h18" />
</svg>
```

Vue:

```vue
<svg role="img" :aria-label="`Rated ${rating} out of 5`" viewBox="0 0 24 24">
  <path d="M3 12h18" />
</svg>
```

### bb-link-name

**Links have accessible names (no empty links).** WCAG 2.4.4, 4.1.2 ([Understanding](https://www.w3.org/WAI/WCAG21/Understanding/link-purpose-in-context.html)) · Tier 1 · checked by Bellbriar, on the markup · basis `sc`: a FAIL is a failure of each criterion the rule cites, one W3C names (a W3C failure technique, or an ACT rule W3C's Working Group approved).

W3C ACT rules: [c487ae](https://www.w3.org/WAI/standards-guidelines/act/rules/c487ae/) Link has non-empty accessible name (approved).

Checks what a browser exposes as a link: &lt;a href&gt; (a drawing's &lt;a&gt; with href or xlink:href too, not MathML's) and anything with role=link (ACT c487ae). Of what a drawing never renders, a link held by a &lt;defs&gt;, a clip path, a mask, a pattern or a marker (or by a &lt;g&gt; or a &lt;marker&gt; whose display is none) is in Chromium 141's accessibility tree, though it takes no focus, and is checked; one held by any other element that renders none of what it holds (a &lt;symbol&gt;, a gradient, a filter, a shape, a &lt;use&gt;, a &lt;desc&gt;), an &lt;a&gt; in an &lt;a&gt;, a text part outside a &lt;text&gt;, and an element of a &lt;switch&gt; after the one it renders are in none and are not checked (each measured). What a &lt;use&gt; copies into the drawing is not checked. A drawing's link is named, after aria-labelledby and aria-label, by its &lt;title&gt; child, then its xlink:title, then what it holds; a &lt;title&gt; or xlink:title of white space alone names it nothing, and nothing after it is read. A link given role=button is a button, checked by bb-button-name, so one unnamed control is one finding (axe-core reports it under link-name); role=none or presentation on a link is ignored, as browsers ignore it on focusable elements and on elements with global ARIA attributes. A name from content reads what an element inside the link holds, whatever its role, as the accessible-name computation does. Chromium 141 reads, of an element whose role holds other content (a &lt;figure&gt;, an &lt;article&gt;, a &lt;nav&gt;, a &lt;header&gt;, a &lt;table&gt; of data, role=group, img and the like), of a &lt;math&gt; and of an &lt;object&gt;, only its own name: its author's (aria-labelledby, aria-label, title) or, for some, its markup's (a &lt;fieldset&gt;'s &lt;legend&gt; or a &lt;table&gt;'s &lt;caption&gt; where shown, a &lt;table&gt;'s summary where it has no &lt;caption&gt;, an &lt;output&gt;'s &lt;label&gt;), each measured. Nor does it read the title of a &lt;span&gt;, a &lt;div&gt;, an &lt;i&gt;, a &lt;p&gt;, an element HTML does not have (an &lt;icon&gt;) and the like there (it reads a heading's, an &lt;abbr&gt;'s, an image's, a custom element's but one whose role is none or presentation), unless the element has a tabindex, is a link, or has a draggable attribute (a &lt;span&gt;, a &lt;div&gt;, an &lt;i&gt;, an &lt;icon&gt; and the like; not a &lt;p&gt;, an &lt;em&gt;, a &lt;code&gt;). A link named only by what such an element holds, or by such a title, is a review that says so: in Chrome and Edge it has no accessible name. It is minor, or moderate where axe-core 4.12 does not read that name either (MathML, text inside an &lt;object&gt;, a &lt;canvas&gt; or a drawing, the title of a &lt;slot&gt; or of an element that holds white space or whose role is none or presentation), and its message gives the reason it found. A &lt;table&gt; is one of data by its markup alone (a &lt;caption&gt;, a &lt;th&gt;, a cell's scope, twenty rows and the like), not by its cells' borders or colors, which the page's styles decide (a border or a bgcolor attribute too). An &lt;svg&gt; in the link gives only its own name too (aria-labelledby, aria-label, its &lt;title&gt;, its title attribute), here as in Chromium (measured), unless browsers honor a role=none or presentation on it, or its role is one named from its content (link, button, heading and the like): then what it holds is read.

**Why it matters.** A link with no text is announced as just "link", or by its address, so screen-reader users cannot tell where it goes, and voice-control users have no name to say to follow it.

**How to fix it.** Give every link text that says where it goes. For a link that shows only an icon, add aria-label (or visually hidden text) and hide the icon with aria-hidden="true".

HTML, before:

```html
<a href="/cart">
  <svg aria-hidden="true" viewBox="0 0 24 24"><path d="M3 3h18"/></svg>
</a>
```

HTML, after:

```html
<a href="/cart" aria-label="Shopping cart">
  <svg aria-hidden="true" viewBox="0 0 24 24"><path d="M3 3h18"/></svg>
</a>
```

React:

```jsx
<a href="/cart" aria-label="Shopping cart">
  <CartIcon aria-hidden="true" />
</a>
```

Vue:

```vue
<a href="/cart" aria-label="Shopping cart">
  <CartIcon aria-hidden="true" />
</a>
```

### bb-button-name

**Buttons have accessible names.** WCAG 4.1.2 ([Understanding](https://www.w3.org/WAI/WCAG21/Understanding/name-role-value.html)) · Tier 1 · checked by Bellbriar, on the markup · basis `sc`: a FAIL is a failure of each criterion the rule cites, one W3C names (a W3C failure technique, or an ACT rule W3C's Working Group approved).

W3C ACT rules: [97a4e1](https://www.w3.org/WAI/standards-guidelines/act/rules/97a4e1/) Button has non-empty accessible name (approved).

Checks what a browser exposes as a button: &lt;button&gt;, button-type inputs and anything with role=button (ACT 97a4e1). A button given role=link is bb-link-name's; a native button given another widget role (tab, menuitem) is still checked here. Image buttons are bb-img-alt's. A name from content reads what an element inside the button holds, whatever its role, as the accessible-name computation does. Chromium 141 reads, of an element whose role holds other content (a &lt;figure&gt;, an &lt;article&gt;, a &lt;table&gt; of data, role=group, img and the like), of a &lt;math&gt; and of an &lt;object&gt;, only its own name: its author's (aria-labelledby, aria-label, title) or, for some, its markup's (a &lt;fieldset&gt;'s &lt;legend&gt; or a &lt;table&gt;'s &lt;caption&gt; where shown, a &lt;table&gt;'s summary where it has no &lt;caption&gt;, an &lt;output&gt;'s &lt;label&gt;), each measured. Nor does it read the title of a &lt;span&gt;, a &lt;div&gt;, an &lt;i&gt;, a &lt;p&gt;, an element HTML does not have (an &lt;icon&gt;) and the like there (it reads a heading's, an &lt;abbr&gt;'s, an image's, a custom element's but one whose role is none or presentation), unless the element has a tabindex, is a link, or has a draggable attribute (a &lt;span&gt;, a &lt;div&gt;, an &lt;i&gt;, an &lt;icon&gt; and the like; not a &lt;p&gt;, an &lt;em&gt;, a &lt;code&gt;). It reads a &lt;label&gt;'s content naming the button so too, and the button's &lt;label&gt; (one whose for names it, or one that holds it as its first labelable element) takes the place of its content, value and title there, an empty or hidden one too, or one that holds the button alone; not one in a &lt;template&gt;, nor one inside a closed &lt;details&gt; or other content Chromium skips, which it leaves out. A submit or reset button's default name (Submit, Reset) names it only where it has no value attribute: an empty value names it nothing, and Chromium reads no title after it. A button named only by what such an element holds or by such a title, by a title after an empty value, or whose &lt;label&gt; names it nothing there, is a review that says so: in Chrome and Edge it has no accessible name. It is minor (a button whose &lt;label for&gt; is hidden, invisible or inside content Chromium skips too, which axe-core passes), or moderate where axe-core 4.12 does not read that name either (MathML, text inside an &lt;object&gt;, a &lt;canvas&gt; or a drawing, the title of a &lt;slot&gt; or of an element that holds white space or whose role is none or presentation), and its message gives the reason it found. An &lt;svg&gt; in the button gives only its own name too (aria-labelledby, aria-label, its &lt;title&gt;, its title attribute), here as in Chromium (measured), unless browsers honor a role=none or presentation on it, or its role is one named from its content (link, button, heading and the like): then what it holds is read.

**Why it matters.** A button with no name is announced as just "button", so screen-reader users cannot tell what it does.

**How to fix it.** Put text in the button. For a button that shows only an icon, add aria-label and hide the icon with aria-hidden="true".

HTML, before:

```html
<button type="button">
  <svg aria-hidden="true" viewBox="0 0 24 24"><path d="M6 6l12 12"/></svg>
</button>
```

HTML, after:

```html
<button type="button" aria-label="Close dialog">
  <svg aria-hidden="true" viewBox="0 0 24 24"><path d="M6 6l12 12"/></svg>
</button>
```

```jsx

</button>
```

```vue

### bb-redundant-links

**No adjacent duplicate links.** WCAG 2.4.4 ([Understanding](https://www.w3.org/WAI/WCAG21/Understanding/link-purpose-in-context.html)) · Tier 1 · checked by Bellbriar, on the markup · basis `policy`: never a FAIL: stricter than WCAG 2.1 AA (a pled pattern, or a WCAG 2.2 criterion), reported for review.

Stricter than bare SC; kept because it is verbatim complaint boilerplate. Never FAILs: reported for review as pled in complaints, not a WCAG failure on its own (a product card with an image link and a title link to the same page conforms). Fix = technique H2 (https://www.w3.org/WAI/WCAG21/Techniques/html/H2). --strict gates the moderate-impact H2 shape.

**Why it matters.** Two links in a row to the same page, such as a product image and its title, make keyboard and screen-reader users pass the same destination twice. Complaints plead this as "redundant links"; it is not a WCAG failure on its own.

**How to fix it.** Combine them into one link (W3C technique H2): put the image and the text in a single &lt;a&gt;, and give the image alt="" so the name is not read twice.

HTML, before:

```html
<a href="/shoes/red"><img src="red.jpg" alt="Red sneaker"></a>
<a href="/shoes/red">Red sneaker</a>
```

HTML, after:

```html
<a href="/shoes/red">
  <img src="red.jpg" alt=""> Red sneaker
</a>
```

React:

```jsx
<a href={`/shoes/${shoe.slug}`}>
  <img src={shoe.image} alt="" /> {shoe.name}
</a>
```

Vue:

```vue
<a :href="`/shoes/${shoe.slug}`">
  <img :src="shoe.image" alt=""> {{ shoe.name }}
</a>
```

### bb-control-label

**Form fields are labeled.** WCAG 4.1.2 ([Understanding](https://www.w3.org/WAI/WCAG21/Understanding/name-role-value.html)) · Tier 1 · checked by Bellbriar, on the markup · basis `sc`: a FAIL is a failure of each criterion the rule cites, one W3C names (a W3C failure technique, or an ACT rule W3C's Working Group approved).

W3C ACT rules: [e086e5](https://www.w3.org/WAI/standards-guidelines/act/rules/e086e5/) Form field has non-empty accessible name (approved).

Fields chosen by role, as ACT rule e086e5 chooses them (P2-09): native fields (&lt;input&gt; other than button and hidden types, &lt;select&gt;, &lt;textarea&gt;) and any element whose role is a form field's (checkbox, combobox, listbox, menuitemcheckbox, menuitemradio, radio, searchbox, slider, spinbutton, switch, textbox), such as &lt;div role="checkbox"&gt;; disabled ones too. A role named by its content (checkbox, radio, switch and the menu items) passes with text; the others need aria-label or aria-labelledby. A field with no accessible name fails 4.1.2, the criterion e086e5 requires; it may fail 1.3.1 (visible text labels it but is not tied to it) or 3.3.2 (nothing visible labels it) as well, which markup alone cannot settle, so a FAIL names 4.1.2 alone. A field named only by its placeholder is a moderate review, pled in complaints: browsers expose the placeholder as the name, so ACT rule e086e5 passes it for its name, but the rule notes that 3.3.2 still needs a visible label that does not disappear as the user types, and markup alone cannot tell whether other visible text labels the field. --strict gates it. A placeholder names only a text field (an &lt;input&gt; of type text, search, tel, url, email, password or number, or of a type HTML does not have) and a &lt;textarea&gt;, in HTML-AAM and in Chromium 141 (measured): a &lt;select&gt;, a date field, a range, a color well or a checkbox with one and no other name fails, though axe-core 4.12 passes an &lt;input&gt; by its placeholder whatever its type (R6AB-4). A &lt;label&gt; names the control HTML makes it label (its for target, or a label without for's first labelable descendant in its own tree, not one a slot in it shows, and none where a slot's fallback held it: R5K-2, R5M-10), by its own aria-labelledby or aria-label first, then by its content (not the control it names: a select's options are not its label), then by its title (R5M-8, R5S-5); a hidden label names nothing (a label shown inside it still does: R5K-1), nor does one inside an element that skips what it holds (hidden="until-found", or content-visibility:hidden, on a box that skips, as a block or an inline block does and an inline element or a table does not; a file run reads content-visibility and display in the style attribute only, a rendered run as the page sets them: R5M-1, R5O-3), as Chromium 141 computes it; a form-associated custom element is labelable too, which markup cannot show, so a label whose first labelable descendant is one is read as labeling the next labelable element in it (R5I-14). Chromium 141 reads a native field's &lt;label&gt; in place of its title and placeholder, an empty or hidden one too, and one inside an aria-hidden element, which the accessible-name computation and axe-core 4.12 leave out (measured: R6AB-1; a field named by such a label alone fails, L128): a field named only by its title past &lt;label&gt;s that name it nothing is a minor review that says so, since axe-core 4.12 passes it (in Chrome and Edge it has no accessible name), and the placeholder's review says so too (L104). A field named only by text in its &lt;label&gt; that Chromium 141 does not read (MathML, an &lt;article&gt;'s text, a &lt;span&gt;'s title) is a review as a button's is: minor where axe-core 4.12 passes it, by its title or placeholder (a &lt;select&gt; by its title alone) or by that text where it is a title axe-core reads; else moderate: axe-core reads no MathML or embedded content into a name, nor the title of a &lt;slot&gt; or of an element that holds white space or whose role is none or presentation, and a &lt;label&gt;'s other content by rules of its own (it fails one holding an &lt;article&gt;, passes one holding a &lt;figure&gt;: R6AB-3).

**Why it matters.** A form field with no accessible name is announced only by its type ("edit text"), so screen-reader users cannot tell what to enter.

**How to fix it.** Give each field a visible &lt;label&gt; tied to it (for and id, or the field inside the label). Where no visible label fits, use aria-label or aria-labelledby. A placeholder is not a label: it disappears as the user types.

<input type="email" id="email" name="email">

### bb-skip-link

**Bypass blocks (skip link).** WCAG 2.4.1 ([Understanding](https://www.w3.org/WAI/WCAG21/Understanding/bypass-blocks.html)) · Tier 1 · checked by Bellbriar, on the markup · basis `heuristic`: a FAIL is a probable failure of the criteria the rule cites: markup alone cannot settle it, or W3C does not itself name it.

W3C ACT rules: [cf77f2](https://www.w3.org/WAI/standards-guidelines/act/rules/cf77f2/) Bypass Blocks of Repeated Content (proposed).

FAILs only when the markup identifies repeated blocks and nothing bypasses them, or the only mechanism is a skip link that leads nowhere or is out of the tab order. The blocks: a navigation that leads the page, the page header (not one inside the page footer), or a sidebar or other block beside the content holding either, with two or more links or controls besides the skip link (a single link is not a block). Bypasses: a working skip link; a main landmark that does not wrap the navigation, or a named region or form landmark the content starts in (ARIA11: the page's first perceivable content past the blocks is inside it; never a search, nor one inside a page header, banner, footer, sidebar or dialog); a heading that opens the content (H69); on a one-page site (no leading navigation links to another page or a hash route, a link home aside), a navigation with at least two links to areas of content past the blocks and no other links but a link home or to the top of the page (G124: sections, articles or headings; no toggles or panels); a control before each leading navigation that may expand and collapse it (SCR28, ACT 3e12e1: focusable, with aria-expanded, naming in aria-controls the navigation, an element around it or one inside it that holds all its links, with no more than one other link or control in the page header and blocks beside the content; L72-13). A missing or broken skip link where a main landmark, another landmark the content starts in, an opening heading, G124 or such a control remains is needs_review, pled in complaints; so is a page whose blocks the markup does not identify (no such navigation or header, 15 or more links outside the page footer), and a working skip link that comes after more than three links or controls of the page header and leading navigation, or, where the markup identifies no blocks, more than ten of any kind (late). The navigation to bypass is one that leads the page: before &lt;main&gt;; without &lt;main&gt;, before the first content heading and before the page's own text passes 200 characters (text and headings before the page header, and the text of form controls, do not count); never breadcrumbs, a sidebar, the footer or a dialog. A skip link is an in-page link, before the end of that navigation, that says it skips; one of the first five links, placed before it, that leads into the content past it (any language); or a link to the end of the navigation with none of its links or controls after the target (G123). With no such navigation, the first five links are read by name, and later ones before the first content heading count only with an unmistakable name ('Skip to content'). A hash route, 'Back to top', a link that opens a panel, a link after the navigation, a link with a negative tabindex (an invalid tabindex is no tabindex), and a target only inside &lt;template&gt; or &lt;noscript&gt; are not working skip links. A button or role=button/link control counts when its name plainly says it skips to the content ('Skip to main content'). A &lt;main&gt; wraps the navigation when the navigation opens it and only in-page links come before it; it then bypasses nothing. A heading opens the content when it is the first named heading after the banner or navigation, outside footer, sidebar and breadcrumb blocks, is not just a link home, and at most three links or controls and a short lead-in of text come before it. Only the page as exposed counts: content behind an open dialog is not evaluated, and the dialog is not the page. Operability of the skip link (visible on focus, moves focus) is interaction-layer. W3C's ACT rule cf77f2 (proposed) passes a page where any one of four holds: every block of repeated content can be collapsed (3e12e1), a heading is in the content past the blocks (047fe0), a landmark holds that content (b40fd1), or an instrument moves focus to it (ye5d6e). This rule follows H69 in wanting the heading to open the content, so a page whose only bypass is a heading further down fails here (a probable failure, heuristic); markup cannot show that a toggle collapses anything, so one makes a review, not a pass (L72-10).

**Why it matters.** Without a way past the header and navigation, keyboard and screen-reader users must go through every one of their links on every page before they reach the content.

**How to fix it.** Make the first link on the page a "Skip to main content" link to the main content's id; it may stay visually hidden until it receives focus. Wrap the content in &lt;main&gt; too, which screen readers can jump to.

HTML, before:

```html
<header>
  <nav>
    <a href="/">Home</a> <a href="/shop">Shop</a> <a href="/about">About</a>
  </nav>
</header>
<div class="content"><p>Fresh bread every morning.</p></div>
```

HTML, after:

```html

<header>
  <nav>
    <a href="/">Home</a> <a href="/shop">Shop</a> <a href="/about">About</a>
  </nav>
</header>
<main id="main"><h1>Welcome</h1><p>Fresh bread every morning.</p></main>
```

```jsx

  <SiteHeader />

Content that is not rendered cannot take focus. Focusable content whose display or visibility a custom property (var()) decides, under a condition too, is a moderate review in a file run, which does not read what a custom property holds; where the page's own styles set that property nowhere and no stylesheet the run cannot read could (the page links and imports none, nor names one in an &lt;?xml-stylesheet?&gt;), the var() is read as its fallback, or as unset where it has none, as a browser reads it, but where a rule that hides the content (display:none, visibility:hidden or collapse, or a revert to what the browser's own stylesheet hides, a var()'s fallback revert too) stands level with it in the cascade, which the run cannot order (it reads no specificity), it is still a review, under a condition too. A closed modal is aria-hidden and hidden together (Bootstrap, Flowbite and Foundation remove both as they open it): a rendered run reports nothing, and a file or server-HTML run, which cannot read linked stylesheets, reviews a container that its own framework class, or a rule in the page's own &lt;style&gt;, says is closed. Focusable content hidden now by a container around or inside the aria-hidden one (a closed menu, tab or panel) is a moderate review in both runs: it becomes focusable when that opens. Each offender is reported once, under its outermost aria-hidden container. ACT rule 6cfa84 requires 4.1.2 for conformance (it maps 1.3.1 as secondary), so a FAIL names 4.1.2. aria-hidden on the page's &lt;html&gt; or &lt;body&gt; hides nothing, since browsers ignore it there, so it is not checked here; a rendered run's bb-aria-hidden-body reviews it on either element (a best practice).

**Why it matters.** aria-hidden="true" hides content from screen readers, but a link or button inside it can still take keyboard focus: users land on something that is announced as nothing.

**How to fix it.** Never put focusable content inside aria-hidden. Take content that is not in use out of use for everyone: the hidden attribute or display: none, or inert where it must stay visible (a carousel's other slides); otherwise remove aria-hidden.

### bb-aria-hidden-body

**The page is not hidden from assistive technology.** WCAG 4.1.2, 1.3.1 ([Understanding](https://www.w3.org/WAI/WCAG21/Understanding/name-role-value.html)) · Tier 2 · checked by axe-core's `aria-hidden-body`, in the browser · basis `best-practice`: never a FAIL: WCAG does not require it on its own (the notes say why), reported for review.

axe-core's aria-hidden-body: aria-hidden="true" on &lt;body&gt;. WAI-ARIA 1.3 (a draft) tells browsers not to expose the hidden state on a document's root element, and Chromium (141, tested), Firefox (from 139) and WebKit (since April 2024) ignore aria-hidden on &lt;html&gt; and &lt;body&gt;: the page stays exposed. An older browser may hide all of it. Reported as a best practice, not a failure (L72-4), at moderate impact at most, on &lt;html&gt; too, which axe-core's rule does not check. The harness's own rules ignore aria-hidden there too, as those browsers do: focusable content in such a page does not fail bb-aria-hidden-focus, and its names are checked. axe-core skips what it takes as hidden (aria-hidden exactly "true" there, as it compares it; color-contrast, which reads what is seen, still checks the page), so on such a page a rendered run reports what axe-core's other rules found failing, and a rule that found no failure there is not evaluated; the page's capture notes and the coverage sentence say so (R5G-1, R5I-7). A file run reads no axe-core rule, this one included.

**Why it matters.** aria-hidden="true" on &lt;body&gt; is an authoring error: current Chromium, Firefox and Safari ignore it there, as WAI-ARIA now tells browsers to, but an older browser may hide the entire page from screen readers.

**How to fix it.** Remove aria-hidden from &lt;body&gt;. To keep users in a dialog, open a &lt;dialog&gt; with showModal(), or make the rest of the page inert; never hide &lt;body&gt; itself.

HTML, before:

```html
<body aria-hidden="true">
  <main><h1>Example</h1></main>
</body>
```

HTML, after:

```html
<body>
  <main><h1>Example</h1></main>
</body>
```

React:

```jsx
// open dialogs with showModal(), which keeps users in them
const dialogRef = useRef(null);
return (
  <>
    <button type="button" onClick={() => dialogRef.current.showModal()}>Open</button>
    <dialog ref={dialogRef}>...</dialog>
  </>
);
```

Vue:

```vue

<dialog ref="dialog">...</dialog>
<button type="button" @click="$refs.dialog.showModal()">Open</button>

**Why it matters.** People with dyslexia or low vision widen letter, word and line spacing with their own styles; !important in a style attribute stops them.

**How to fix it.** Do not set letter-spacing, word-spacing or line-height with !important in style attributes; set them in your stylesheet.

HTML, before:

```html
<p style="letter-spacing: 0.02em !important">Terms and conditions apply.</p>
```

HTML, after:

```html
<p class="small-print">Terms and conditions apply.</p>
```

React:

```jsx
// styles.css: .small-print { line-height: 1.5; }
<p className="small-print">Terms and conditions apply.</p>
```

Vue:

```vue
<template>
  <p class="small-print">Terms and conditions apply.</p>
</template>

<style scoped>
.small-print { line-height: 1.5; }
</style>
```

### bb-reflow-320

**Reflow at 320 CSS pixels.** WCAG 1.4.10 ([Understanding](https://www.w3.org/WAI/WCAG21/Understanding/reflow.html)) · Tier 2 · checked by Bellbriar, in the browser · basis `heuristic`: a FAIL is a probable failure of the criteria the rule cites: markup alone cannot settle it, or W3C does not itself name it.

Bellbriar's own check, in the browser (L24): just after the capture the page is narrowed to 320 by 640 CSS pixels, and the capture records the page's scroll width there and each outermost element reaching past the right edge (outside anything that clips or scrolls sideways, and not fixed to the viewport). A page that scrolls sideways at 320 px FAILs, as a probable failure: content that needs two dimensions is exempt, so where a table, image, map, video or code holds the overflow the finding is a review. A page that hides its overflow (overflow-x: hidden) does not scroll and is not reported, so content cut off there is not detected. 1.4.4 (resize text to 200%) is not tested. No ACT rule requires 1.4.10: ACT rule b4f0c3, on zoom in the viewport meta tag, maps it as a secondary requirement (L72-6, H6-8).

**Why it matters.** Someone who zooms to 400% sees the page about 320 CSS pixels wide. Content that does not reflow makes them scroll sideways to read every line.

**How to fix it.** Use flexible widths (max-width: 100%, flex or grid that wraps) instead of fixed pixel widths, and let long words break (overflow-wrap: anywhere).

HTML, before:

```html
<div style="width: 1000px">
  Order before noon for delivery the same day across the whole city.
</div>
```

HTML, after:

```html
<div style="max-width: 1000px">
  Order before noon for delivery the same day across the whole city.
</div>
```

React:

```jsx
// styles.css: .banner { max-width: 1000px; }
<div className="banner">Order before noon for delivery the same day.</div>
```

Vue:

```vue
<template>
  <div class="banner">Order before noon for delivery the same day.</div>
</template>

<style scoped>
.banner { max-width: 1000px; }
</style>
```
